## 6. 项目技术定位

**AI 应用 / RAG 工程为主，后端工程为辅，含完整前端。**

一句依据：整个系统的技术重心在**检索质量、生成可信度与质量评测**这三件事上——混合召回、精排、引用校验、评测与消融占了代码与文档的大头；而后端（FastAPI + 异步 + 关系库）与前端（React + 流式渲染）是为了支撑这三件事而存在的外壳。

技术栈速览：

| 层 | 技术 |
|---|---|
| 编排 | LangGraph（状态图 + 条件边，无检查点） |
| 检索 | Chroma（本地持久化向量库）、bm25s（jieba 分词稀疏索引）、BAAI/bge-reranker-v2-m3（交叉编码器） |
| 模型 | DeepSeek（生成 / 改写 / 消解 / 路由，非思考模式）、通义千问（嵌入 1024 维）、MinerU（扫描件 OCR） |
| 服务 | FastAPI + asyncpg（原生 SQL，无 ORM）、JWT 鉴权、SSE 流式 |
| 存储 | PostgreSQL（元数据 / 会话 / 日志）、Chroma、bm25s 三存储 |
| 评测 | 自建规则指标 + ragas（隔离虚拟环境，子进程调用） |
| 观测 | Langfuse（追踪 + 指标回查 + 阈值告警） |
| 前端 | React 19 + Vite + zustand + Tailwind/shadcn + pdf.js 原文预览 |

## 7. 核心原理解析

### 7.1 混合召回为什么必要，融合为什么要用排名而不是分数

**问题**：稠密向量擅长语义相近，但对"桂电教〔2025〕28号"这种**字面精确串**不敏感——文号里的数字与符号在嵌入空间几乎没有区分度；反过来，稀疏检索对同义改写无能为力。

**机制**：两路各召回一批候选，用**倒数排名融合**合并：`分数 = Σ 权重 / (常数 + 该路排名)`。关键在两点——① 只用**排名**不用原始分数，因为余弦相似度和 BM25 分根本不同量纲，直接加权求和等于让量纲决定结果；② **去重键是片段 ID**，同一个片段被两条查询多路命中时分数自然累加，这正是"多查询扩展"价值的来源。

**在本项目中的落点**：`backend/app/retrieval/fusion.py` 实现融合，权重被强制固定为 1.0——不是懒得调，而是**只有权重相等，消融表里三种查询类型的增益才归因得清**。融合后截断到 40 条进精排，精排再取 5 条进上下文组装。

> 面试延伸：如果让你加权，你会怎么定权重？答"用消融网格搜索、并接受它会让归因变复杂"，比答"拍一个 0.7/0.3"好得多。

### 7.2 过滤发生在取 Top-N 之后，所以必须过采样重试

**问题**：向量库的元数据过滤是**先取 Top-N 再筛**。如果按"要 10 条"去取 10 条，其中 6 条因权限或生效日期被筛掉，实际只剩 4 条——召回看着在跑，其实被悄悄削掉了一半。

**机制**：固定过采样 3 倍取 30 条；如果筛完还不到目标条数，再用 6 倍取 60 条重试一次（替换而非追加）。

**在本项目中的落点**：`backend/app/retrieval/search.py`。另一条腿（稀疏检索）**不需要**过采样——它是全量打分后按文档粒度过滤再取 K，过滤与排序的顺序本来就不同。**"两路过滤位置不同"是这条链上最容易被面试官追问的细节。**

### 7.3 内容已经流出去了，校验只能"标注"不能"拦截"

**问题**：为了体验，答案是逐字流给用户的；但"这句话有没有依据"的校验只能在答案生成完之后做。等发现问题，文字已经在屏幕上了——**流式与后校验天然冲突，任何"事后撤回"的设计都是假的**。

**机制**：把冲突显式化，定位成"标注而非拦截、度量而非纠正"。具体三件事：① 引用编号**不由模型输出**，只从正文里的标记派生（同一信息编码两遍会互相矛盾，还能绕过校验）；② 越界判定用**证据条数**做上界，而不是候选条数（候选可达 40 条，用它会漏掉"只有 5 条证据却写第 7 条"）；③ 输出"结论句 vs 已引用/未引用"的校验报告，前端把未证实的句子做灰底标注。

**在本项目中的落点**：`backend/app/graph/nodes/cite.py` 产出引用与校验报告，`frontend/web/src/markdown/uncitedAnnotation.ts` 负责定位标注，并且带**双重自检**——标注前后可见文本必须一字不差，定位校验不过就整体放弃标注（"宁可不标，也不要标错"）。

### 7.4 评测要用消融，而不是前后对比一次总分

**问题**："我加了精排，指标涨了"这种说法站不住：涨的可能是噪声，也可能是同时改的另一个变量。

**机制**：① **累积消融**——八行配置逐层打开（纯向量 → 加稀疏 → 加融合 → 加精排 → 加三种查询扩展），每行只与上一行差一个开关；② **最后一行刻意重复上一行配置**，用来测这组指标的**噪声底**——没有这一行，任何小于噪声的"提升"都无法证伪；③ **单路对照**——只看总量发现不了"两路看着都在跑、实际只有一路有效"这类问题，必须同时报每条腿单独的指标；④ **反证实验**——证明"管理员不是后门"时，特意加了一腿"管理员不提权也应该命中 0 条"。

**在本项目中的落点**：`backend/tools/run_ablation.py`（消融）、`backend/app/eval/runner.py`（指标）、`backend/tools/run_acl_experiment.py`（三腿反证）、`docs/检索基线.md` 与 `docs/多轮指代评测.md`（含单路对照与"如实记录融合未超出单路"的自述）。

### 7.5 检索期权限和原文访问必须共用一套判定

**问题**：只把检索锁住是不够的——原文下载、文本导出、图片读取是**绕过检索期权限的捷径**。如果那里另写一套判定，两套迟早不一致，"检索期数据隔离"就被这条捷径架空。

**机制**：过滤条件**只在一个模块生成**，三处共用：向量检索、稀疏检索的文档粒度过滤、用户端原文访问。过滤公式统一为"状态有效 **且** 已生效 **且**（公开 **或** 当前角色可见）。不可见一律返回 **404 而不是 403**——让"不可见"和"不存在"不可区分，否则可以被用来探测文档是否存在。

**在本项目中的落点**：`backend/app/retrieval/filters.py`。两个容易讲错的细节：① 两个检索路的过滤位置不同（一路在检索器内部作为过滤条件，另一路在应用层按文档粒度套用同一份条件）；② 日期在向量库元数据里必须存成**整数**（如 `20251013`）——向量库的比较运算符不接受字符串，而这个错误**只在运行时暴露且被降级链静默兜住**，表面看只是"召回少一点"。这个坑本项目真实踩过（`filters.py:65-81` 有完整记录）。

### 7.6 异构多存储的一致性靠顺序和状态机，不靠事务

**问题**：三个存储（向量库 / 稀疏索引 / 关系库）无法原子提交。写入到一半失败，如果半成品能被检索到，用户就会拿到指向不存在内容的引用。

**机制**：① **写入顺序**——关系库先建行并标记为"建索引中"，再写向量库，再写稀疏索引，**最后**把状态翻成"生效"。因为检索条件要求状态为"生效"，未完成的行天然被排除，不可能以半成品出现；② **失败走补偿删除**，删除顺序与写入完全相反，且**待删的片段 ID 必须向稀疏索引自己查**——从向量库反推会在向量库已空时得到空列表，留下孤儿；③ 失败时关系库的行**只置为失败、永不删除**，因为它承载"传过但失败了"这个事实，删了就分不清"没传过"和"传失败"。

**在本项目中的落点**：`backend/app/ingestion/pipeline.py`（顺序与失败分支）、`backend/app/services/index_service.py`（写入与删除的对称实现）。

## 8. 关键设计决策

| 决策 | 备选方案 | 取舍 | 风险 | 怎么验证 |
|---|---|---|---|---|
| 反链采用"混合召回 + 融合 + 精排" | 只用向量；只用稀疏；向量后加规则重排 | 多两条外部依赖、多一层延迟，换精确串召回与排序质量 | 两路都退化时会**静默**变成单路，指标只掉一点看不出来 | 单路对照指标 + 消融表；本项目已记录"某次日期类型错误导致向量路全部降级、混合检索实际从未生效" |
| 版本折叠放在**检索期**，而不是入库时给旧版打"已废止"标 | 入库时标记旧版失效 | 检索期多一次关系库回查，换"禁用新版可自动恢复上一版" | 折叠基准若从召回集内取最大值，会把**已废止的旧版当成现行版**返回 | 折叠基准强制回查关系库；检索与后台使用**同一条**取现行版的语句 |
| 引用编号由**正文标记派生**，不让模型单独输出编号列表 | 模型输出 `citation_numbers` 字段 | 少一个可被模型操纵的字段，但需要服务端解析正文 | 正文标记可能越界/重复，需要显式校验与报告 | 校验报告落库并可前端展示；越界用证据条数做上界 |
| 澄清恢复用**重新进图**，不用流程框架的中断恢复 | 用 `interrupt()` + 检查点 | 实现简单、历史就是普通消息，但每轮要重建状态 | 会话里会多出"反问 + 回答"两轮，历史长度增长更快 | 多轮评测集里有专门的澄清链路用例 |
| LLM 裁判跑在**独立解释器子进程** | 装进主环境 | 多一套环境要维护、走 JSON 进程间通信 | 环境缺失时指标静默不可用 | 环境缺失返回"不可用"而非抛错；实测两条硬阻断（一条是 import 直接失败，一条是装进主环境后加载重排模型所依赖的库会段错误） |
| 服务**强制单进程** | 多进程横向扩展 | 无法靠加进程提吞吐 | 向量库是进程内嵌打开本地文件，多进程会抢同一份文件 | 代码注释与部署约束显式声明；吞吐靠异步与显存信号量而不是多进程 |
| 失败时关系库行**保留**为失败态 | 直接删除失败记录 | 行数会累积、需要一份"失败"视角的查询 | 管理端需要同时展示失败与重复两种非终态 | 管理端文档列表包含失败状态筛选 |
| 模型调用**不自动重试** | 统一加重试 | 少一层放大故障的可能，但单次抖动直接降级 | 用户会在偶发抖动时拿到降级结果 | 降级有统一词汇表并落库，可统计降级率；只有嵌入接口保留指数退避重试 |
| 所有阶段事件与内部节点名**解耦** | 直接把节点名当阶段名 | 多一份映射表要维护 | 映射漏了某个节点会导致前端缺阶段提示 | 有专门的图追踪与阶段事件回归用例 |
