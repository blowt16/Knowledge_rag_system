# 日志追踪使用说明

本文说明后端控制台日志怎么看、怎么调、怎么用 `trace_id` 串起一次请求。

实现设计见 `docs/superpowers/specs/2026-10-19-log-tracing-design.md`。

---

## 1. 控制台一行日志怎么读

```text
18:31:05.772 INFO  [a1b2c3d4] retrieve    ✔ 完成 2.72s   candidates=17
```

| 列 | 含义 |
|---|---|
| `18:31:05.772` | 本地时间，精确到毫秒 |
| `INFO` | 日志级别（DEBUG / INFO / WARNING / ERROR） |
| `[a1b2c3d4]` | `trace_id` 前 8 位；同一次请求的所有行都一样 |
| 缩进 | 阶段层级：HTTP/chat 在最左，图节点缩进 2 格，子阶段再缩进 2 格 |
| `retrieve` | 阶段名（ASCII，方便 grep） |
| `✔ 完成` / `✖ 失败` | 阶段状态 |
| `2717ms` | 阶段耗时；超过 1 秒显示为 `2.72s` |
| `candidates=17` | 关键字段；只放数量、耗时、枚举，不放正文；空值自动省略 |

失败行示例：

```text
18:31:05.772 ERROR [a1b2c3d4] retrieve    ✖ 失败 2717ms  candidates=0 error=TimeoutError
```

错误堆栈只写进 `logs/app.jsonl`，控制台只显示错误类型，避免刷屏。

## 3. 用 trace_id 排查

- 响应头 `x-trace-id` / `traceparent` 里的值，与控制台 `[...]` 里的前 8 位同源。
- 控制台的 `chat.start` 行会打印完整 `trace_id`；复制它可以直接：
  - 在 `logs/app.jsonl` 里搜 `"trace_id": "<完整值>"`；
  - 在 Langfuse 里搜同一条 trace。
- Langfuse 关闭时也会生成本地 `trace_id`，不再是一串 0。

## 4. 配置

`backend/app/config/app.yaml`：

```yaml
logging:
  default_level: INFO
  console_level: DEBUG       # handler 最低级别；实际仍受 LOG_LEVEL/root 控制
  console_format: text       # text | json
  console_color: auto        # auto | always | never
  console_max_value_chars: 120
  trace_content: true        # DEBUG 档是否输出 query / chunk 正文
  trace_content_max_chars: 300
```

常用组合：

| 场景 | 设置 |
|---|---|
| 日常开发，看主流程 | 默认 `INFO` |
| 排查检索/精排细节 | `LOG_LEVEL=DEBUG` |
| 控制台太吵，只看文件 | `console_level: WARNING` |
| 终端颜色乱码 | `console_color: never` |
| Docker / 采集 JSON | `console_format: json` |

> `console_level` 不能低于 root 级别；要看 DEBUG 子阶段必须设 `LOG_LEVEL=DEBUG`。

## 4.1 DEBUG 内容日志（默认开启，仅 DEBUG 档输出）

`LOG_LEVEL=DEBUG` 时，每个节点会额外输出一行/多行 `*.detail`：

```text
DEBUG [3151c589]   resolve.detail · 消解结果  skipped=yes query=转专业的申请条件是什么 resolved_query=转专业的申请条件是什么
DEBUG [3151c589]   route.detail   · 路由结果  route=knowledge source=rule clarify_skipped=no
DEBUG [3151c589]   rewrite.detail · 改写查询 1/3  source=verbatim target=both query=转专业的申请条件是什么 rank=1
DEBUG [3151c589]   rewrite.detail · 改写查询 2/3  source=keywords target=bm25 query=转专业 申请条件 rank=2
DEBUG [3151c589]   retrieve.chunk · 召回 1  rank=1 score=0.0312 chunk_id=... document=... page=4 text=...
DEBUG [3151c589]   rerank.topk    · Top-K 1  rank=1 score=0.543 chunk_id=... document=... page=4 text=第九条 学院根据...
DEBUG [3151c589]   context.evidence · 证据 1  rank=1 score=0.543 chunk_id=... text=...
DEBUG [3151c589]   generate.detail · 生成结果  decision=ANSWERED answer_preview=申请转专业的学生应...
DEBUG [3151c589]   cite.detail    · 引用 1/2  rank=1 marker=1 document=... page=4 chunk_id=...
```

| 节点 | DEBUG 详情 |
|---|---|
| resolve | 原始 query、消解后 query、是否跳过/未解析 |
| route | route、route_source、clarify_skipped |
| rewrite | 每条改写查询的 source/target/text |
| retrieve | 每个候选 chunk 的 rank/score/chunk_id/document/page/text |
| rerank | **Top-K 每个 chunk** 的 rank/rerank score/chunk_id/document/page/text |
| build_context | 每个 evidence chunk 的 rank/score/text |
| generate / chat | decision、answer 前 300 字 |
| cite | 每条引用的 marker/document/page/chunk_id |
| refuse | 拒答原因 |
| clarify | 澄清问题与 facets |

控制项：

```yaml
logging:
  trace_content: true          # 关闭后即使 DEBUG 也不输出正文
  trace_content_max_chars: 300 # 每条 query/text/answer_preview 的截断长度
```

> ⚠️ DEBUG 档会把 query / 改写内容 / 检索片段写进**控制台**。`logs/app.jsonl` 里
> `query` / `resolved_query` / `text` / `answer_preview` 仍按敏感键打码。生产环境请设
> `trace_content: false`，并不要长期开启 DEBUG。

## 5. 隐私约束

- 默认 INFO 档不记录 query / answer / prompt / 检索正文；query 只记 `query_len` 和 `query_hash`。
- 显式开启 `LOG_LEVEL=DEBUG` 且 `trace_content: true` 时，控制台会输出 debug 正文（见 4.1）；JSON 文件仍对敏感键打码。
- 所有字段值截断到 `console_max_value_chars`，并去掉换行，防止日志注入。
- 需要看正文时，用 `trace_id` 去 `qa_logs` 或 Langfuse 查；那里有 ACL 和脱敏约束。

## 6. 审计日志（P0）

管理端写操作与安全事件统一用 `event=audit.<module>.<action>`，成功 `INFO`、失败 `WARNING`：

```text
INFO  [16a04d8b] audit.user     ✔ 审计 actor_id=admin-1 target_id=u1 username=alice role=student
WARN  [16a04d8b] audit.auth     ✖ 审计 reason=invalid_credentials username=bob
INFO  [16a04d8b] audit.document ✔ 审计 actor_id=admin-1 target_id=d1 changed_fields=visibility title=... visibility_before=public visibility_after=restricted
```

已覆盖：

| 事件 | 内容 |
|---|---|
| `audit.auth.login` / `audit.auth.refresh` / `audit.auth.logout` | 成功/失败、user_id、username、role、失败原因 |
| `audit.auth.token` | 缺失/过期/无效/撤销令牌，失败原因 |
| `audit.auth.forbidden` | 角色不足，actor、所需角色 |
| `audit.user.create` / `update` / `reset_password` / `delete` | actor、target、角色/可用性变更前后、删除的会话/消息数 |
| `audit.document.update` | visibility/status/effective_date/roles 变更前后、是否重索引 |
| `audit.document.delete` | actor、标题、版本、Chroma/BM25 删除计数 |
| `audit.conversation.delete` | 会话所有者与 session_id |
| `audit.eval.set.delete` | actor、set_id/name、级联用例数 |
| `audit.eval.run.delete` | actor、run_id/name/status、级联结果数 |

审计日志只记 ID、枚举、字段名、计数，不记密码/正文。

## 7. 常见问题

**控制台只有 JSON？**
`console_format` 被设成了 `json`，改回 `text`。

**看不到子阶段？**
默认 INFO 只显示主流程；设 `LOG_LEVEL=DEBUG`。

**一次请求的 trace_id 是 `--------`？**
说明日志不在任何 trace 上下文里（例如启动日志、CLI 外部调用）。请求内不会出现。

**uvicorn 的访问日志去哪了？**
已关闭默认 access logger，由 `http` 阶段行统一输出，避免每个请求两行。
